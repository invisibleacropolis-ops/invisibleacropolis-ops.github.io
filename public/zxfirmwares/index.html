PROJECT 01 / OFFLINE SOUND EXPERIMENT

Experimental tape / codec lab

The recovered conversation explores a four-track, S-4-inspired sample-mangler and roughly 30-second captures. Start by listening: compare PCM16, linear PCM8, independent-block IMA4 and BRR; explore fidelity, duration, decoder size and seeking as separate trade-offs; try reverse, slices and varispeed. This is an audio prototype, not a four-track implementation or an FM-1 CPU emulator.

No microphone or device access. Audio stays in memory and is not uploaded. Playback is opt-in at 25% gain: lower your listening volume first. Full decoded audio is held in browser RAM; this does not establish on-device streaming feasibility.

Quality is a spectrum, not one preset

CD-format PCM is 44,100 samples/s × 16 bits × 2 channels = 176,400 bytes/s. A hypothetical 512 KiB audio-only pool holds about 2.97 seconds; the entire 1 MiB would hold about 5.94 seconds before firmware/protected data. Lossless compression depends on the recording. BRR at 44.1 kHz is still lossy, not CD fidelity.

  1. Exact reference: native-channel PCM and bit-exact FLAC host round trips; establish hard capacity limits.
  2. Waveform ladder: rate/bit-depth/IMA/BRR sweeps on identical clips, with real headers and restart costs.
  3. BRR optimization: filter/range search, reset intervals and later lookahead/perceptual encoder experiments; keep decoder fixed.
  4. Listening gate: level-matched, blinded comparisons on speech, drums, sustained/acoustic sounds and mixes; no “hi-fi” verdict from SNR alone.
  5. Demoscene branch: reusable samples, small scores, procedural instruments, wavetables/LPC/partials and hybrids. A recipe for an original sound is not a tiny lossless encoding of arbitrary audio.
  6. Target frontier: measure code + data + RAM + decode/seek time + playback load, then emulate and only later validate approved hardware candidates.

ISOLATED COMPARISON CANDIDATE / 0.5

Fit the sound, then repair what is missing

This version estimates tonal components directly from PCM—no note labels or generator recipes—then renders quantized parameters through the same C code natively and in WASM. Independent 2,048-frame pages contain up to four linearly varying sine/cosine coefficient pairs; 256-frame BRR repairs are selected by measured error reduction per byte.

Enable the optional experiment below to compare model-only, dense repair and an objective-SNR-target candidate against flat BRR. Full headers, directory, parameters and patches are counted; dominated candidates fall back to flat BRR. Noise, attacks and dense mixes may need more bytes or miss the target. Mono host prototype, not a perceptual hi-fi result, real-time target test or complete firmware decoder. Main remains at the previous baseline for comparison.

CUSTOM PIPELINE / WORKING CONCEPT

BRR + reusable atoms + procedural markers + residual repair

The goal is convincing high-fidelity reconstruction from a compact representation, with heavy PC analysis and a bounded firmware renderer. Start with a better BRR encoder, then test whether repeated atoms, oscillator trajectories and shaped-noise envelopes can replace expensive waveform data. Preserve difficult attacks and unpredictable detail with measured BRR residuals.

Implemented now: beam search through the unchanged BRR decoder, with whole-clip SSE fallback; exact repeated-page markers which regenerate identical BRR bytes and never increase file size; Candidate A adds PCM-fitted tonal models and sparse BRR repair. Planned: approximate atom transforms, frequency trajectories/noise, bandwidth extension, stereo allocation and perceptual residual optimization. No arbitrary-music hi-fi result is claimed yet.

  • Strict BRR route: improve coding decisions at the same 9 bytes / 16 samples; decoder stays unchanged.
  • Exact marker route: store an independent BRR page once, reference it at multiple times. Reconstructed BRR is identical; nonrepetitive inputs fall back to flat BRR.
  • Hybrid route: regenerate predictable tonal/noisy components from parameters; spend residual bits on what the model misses. Adding a model beside a full-rate BRR stream alone does not save bytes.
  • 30-second targets: 64/96/128 kbit/s total correspond to 240,000/360,000/480,000 bytes before extra container/index overhead. They are experiment budgets, not quality promises.

Relevant research includes ADPCM-XQ lookahead/noise shaping, spectral modeling synthesis, DDSP analysis-by-synthesis, bandwidth extension, and pulsejet’s size-constrained decoder approach. Our marker interpreter is currently a host JS prototype; its firmware port and cost are still to be measured. Exact random seeds cannot encode arbitrary unknown waveforms for free.

SAFETY / NO WRITE TRANSPORT

Recovery is a prerequisite, not a guess

This workbench intentionally cannot enumerate MIDI ports, send SysEx, modify voltage or clocks, or write firmware. The original handshake bytes, erase map, OCT-key recovery shortcut, Pico pulse parameters and unsigned-boot claims are not accepted as validated instructions.

Before any hardware write

  1. Identify exact model, current firmware and known board revision.
  2. Obtain and hash model-specific stock inputs; record provenance and redistribution restrictions.
  3. Make independently checked unit-specific backups, including calibration and identity data; keep them private and backed up outside Git.
  4. Verify the address coordinate system, protected ranges and model gates from the actual package and reviewed loader.
  5. Document a recovery procedure validated for this revision. A browser simulation is not recovery evidence.
  6. Review the build, update path, power-loss behavior and acceptance plan before explicitly approving a flash.

Current no-go conditions

  • Exact owner model, per-track duration and mono/stereo policy not confirmed.
  • No owner-unit backup or validated recovery recorded.
  • No local firmware compilation or installable candidate produced.
  • FM-1 and SMK firmware images must not be interchanged.
  • README maintainer reports do not establish universal Pro/Elite hardware validation.

Public publication is also gated: review the allowlisted dist/ artifact before transferring it to the separate GitHub Pages repository. A private repository does not make a public Pages site private.
